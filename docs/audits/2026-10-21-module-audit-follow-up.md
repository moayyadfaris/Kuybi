## Why the partial fixes are not closed

### A06: database rollback is improved; cross-process revocation still needs a guarantee

`PasswordResetService` now uses the same transaction manager for the token claim, password/history writes, outbox email, and session revocation. `PasswordChangeService` does likewise for its relevant writes. These are substantive fixes, and the new integration tests inject history/session failures to check rollback.

The admin path is different: `AdminPasswordManagementService.persistPassword()` opens the password transaction, but `UserCredentialsResetListener` calls `revokeAllSessions()` without that manager. Its sessions can commit independently; a later password rollback logs the user out anyway. More importantly, reset/change invalidate session caches only after the password transaction returns. Process death between commit and invalidation can leave a previously cached active-session answer usable until its 30-second TTL. This is a bounded residual window, not the old indefinitely missed database revocation.

Close the remaining acceptance conditions with atomic authoritative revocation/credential versioning and reliable cache semantics; test process interruption, not only method exceptions. If this bounded window and conservative admin logout are accepted product tradeoffs, document that explicitly rather than describing all flows as fully atomic.

### A07: fence validation must precede visibility of the value

At `src/core/cache/services/cache.service.ts:146`, `await this.set(key, value, ttl)` runs before the Lua script validates the captured fence. A reader can get that value before the script removes it. A controlled local probe produced:

```text
visibleBeforeFenceValidation = { status: 'published-old' }
kept = false
afterFenceValidation = undefined
```

Thus the change prevents the usual long-lived stale refill but does not eliminate exposure during publication. The probe used cache-manager/Redis doubles to pause the script; no production Redis instance was touched. Publish and validate atomically, or make reads reject provisional/version-invalid entries. Also account for the five-minute fence TTL if cache fills are not strictly bounded below that duration.

### A14/A17: mitigation is not the original guarantee

Three retries for outcome persistence reduce idempotency failures, but the business write and saved outcome still commit separately. The new code explicitly permits execution again after lease expiry when persistence fails. That is not crash-safe retry deduplication.

Queue configuration now accurately reflects BullMQ semantics, and the email worker has a real limiter. Job-wide attachment processing limits/deadlines still need implementation or an explicit revised operational contract.

### A21: a soft-deleted row still reaches public ACL finalization

`applyCurrentVisibility()` at `attachment.processor.ts:145` checks whether the row exists and whether its visibility matches the last applied value. It never checks `deletedAt`. The attachment entity uses a normal nullable column for deletion, so `findById(..., { bypassCache: true })` can return that row.

A controlled invocation supplied a row with `deletedAt` set and `isPublic: true`; the method called `setAcl('key', true)`. This can occur after a soft delete during processing. Hard deletion during final ACL application also exits on a missing row without reconciling outputs. Serialize/fence finalization with deletion and visibility changes; make deletion terminal for the processing generation.

## Verification performed

- `npm run test:unit -- --runInBand --silent` under Node 24.22.0: **56 suites / 420 tests passed**. Local socket access was enabled for the HTTP helper test. Expected error-path logs and loader warnings appeared; no test failed.
- `npm run typecheck` under Node 24.22.0: **passed**.
- Direct runtime probes: confirmed A01/A09 changed from vulnerable to rejected; reproduced remaining A02/A03 and the residual A07/A21 cases above.
- Compared source changes and reviewed new integration tests for roles, credential atomicity, email URLs, cache fences, idempotency, readiness, outbox, and real worker events. **Those integration tests were not run.** Their common setup drops/recreates the configured database schema, so this check did not run it against an existing developer database.
- No product fixes, migrations, load tests, deployment, or live S3/SMTP requests were performed. The original audit remains historical; this document records current status.

Prioritize the remaining high-risk authorization and upload findings (A02–A05), then complete the partial security fixes (A06/A07/A21). Passing the larger unit suite is useful regression evidence, but it does not close the unchanged findings or the reproduced concurrency gaps.
